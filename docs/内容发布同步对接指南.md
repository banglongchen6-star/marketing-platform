# 离火品宣 → 运营数据库：内容发布同步对接指南

> 日期：2026-10-19　接口版本：1.0
>
> 数据来源：https://pinxuan.shiganneibu.com
>
> 接收系统：https://yunying.shiganneibu.com
>
> 当前交付：2026-10-19已获授权发布品宣端接口，正式部署与密钥启用结果会补记到本文。运营系统代码由同事管理，接收端还需实施；品宣接口上线不等于运营系统已经开始同步。

## 1. 要实现什么

运营系统建立一份“品宣内容发布”的同步副本：首次带入全部历史数据，以后定期同步新增、修改和删除。建议每5分钟执行一次，并提供“立即同步”“最近成功时间”“同步失败原因”入口。

数据由品宣系统维护，运营系统只读展示来源字段；运营系统自己的备注、分类、分析结论另存。公司账号发布独立存放，不混入达人合作费用和达人发布统计。

这份文档可以直接交给运营系统开发者或AI。对接方只需修改运营系统，不能通过本接口修改品宣系统。

## 2. 分工和启用顺序

### 品宣系统维护者

以下是首次启用/维护步骤。收到已签发密钥的运营系统同事直接使用交付值，不要再次生成或替换品宣端密钥。

1. 将本次 `content-publications-api.js`、`server.js`、部署工作流、HANDOFF和本文一并发布。
2. 生成一个随机256位专用密钥（64个十六进制字符），保存到GitHub仓库的Actions Secret：`CONTENT_SYNC_TOKEN`。
3. 当前部署工作流会将这个Secret传给服务器上新启动的 `marketing-platform` 进程；Secret未配置/格式不符时，仅同步接口返回503，原系统照常工作。
4. 将密钥通过双方认可的私密渠道交付接收端维护者。密钥值不要放在本文、Git、浏览器代码、网址参数、截图或普通日志里。不要交付管理员密码或原 `/api/data` 登录令牌。
5. 重新部署后方可正式使用。变更/移除Secret也需要重新部署才对运行中的进程生效。

密钥示例生成方式（在受控电脑终端执行，只写权限600的临时文件，不打印值）：

```sh
node -e 'require("fs").writeFileSync("/private/tmp/pinxuan-content-sync.key", require("crypto").randomBytes(32).toString("hex"), {mode:0o600,flag:"wx"})'
gh secret set CONTENT_SYNC_TOKEN --repo banglongchen6-star/marketing-platform < /private/tmp/pinxuan-content-sync.key
```

`flag:"wx"`避免覆盖已有密钥。完成私密交接后移除临时文件。若不使用GitHub自动部署，也可以在启动Node/PM2的环境中设置同名变量，但不要同时维护两套互相覆盖的配置。

### 运营系统开发者

- 只在后端保存配置（名称建议如下）：
  - `PINXUAN_CONTENT_API_URL`：下方完整HTTPS地址。
  - `PINXUAN_CONTENT_SYNC_TOKEN`：对方私密交付的专用密钥。
- 在后端定时任务中调用接口，写入运营系统自己的数据库。
- 前端通过运营系统自己的权限接口读取同步结果。不能在浏览器直连品宣接口，也不能使用 `NEXT_PUBLIC_*` 暴露密钥。
- 接收端完成首次导入并核对后，才开放给员工使用。当前文档不假设你们使用哪种数据库/ORM。

## 3. 接口

```text
GET https://pinxuan.shiganneibu.com/api/integrations/v1/content-publications
Authorization: Bearer <专用密钥>
Accept: application/json
```

- **全量快照**：所有历史月份、所有平台，不按当前登录人/月份/平台筛选。
- 不接受查询参数，不分页。不要添加 `month`、`since`、`page`、`t` 等参数，接口返回400。
- 仅GET。新增、删除、修改都不能通过此接口进行。
- 建议超时30秒、单实例最多一个同步任务，避免并行任务把旧快照覆盖到新快照上。
- 响应使用 `Cache-Control: private, no-store`，不做公开缓存。

### 响应码

| 状态 | 含义 | 接收端动作 |
|---|---|---|
| 200 | 完整JSON快照 | 校验成功后，在事务里更新副本 |
| 304 | 与上次成功落库的ETag相同 | 不修改数据；记录本次检查成功 |
| 400 | 携带了不支持的查询参数 | 修正调用；保留原数据 |
| 401 | 同步密钥不匹配 | 检查后端配置；保留原数据 |
| 405 | 方法不是GET | 修正调用；保留原数据 |
| 503 + `integration_not_configured` | 未配置有效专用密钥 | 联系品宣维护者启用 |
| 503 + `snapshot_unavailable` | 数据文件读取、解析或结构校验失败 | 保留原数据，至少60秒后重试 |
| 404/其他错误/超时/HTML响应 | 路径、版本、网络或服务异常 | 全部视为失败，绝不按空数据处理 |

首次不带 `If-None-Match`。成功提交数据库事务后保存响应的ETag；后续请求原样带回 `If-None-Match`。必须保存完整值，包括 `W/` 和引号。304没有JSON正文。

ETag是业务内容的指纹；`generated_at`每次不同不会使ETag变化。`snapshot_id`不是可排序的时间或数据库版本号。禁止用它判断先后。

## 4. 返回结构

以下为**结构示意**，省略了记录内部字段，不是用于导入的完整样例：

```js
{
  schema_version: "1.0",
  source: "pinxuan",
  environment: "production", // 本地隔离预览为local-preview，正式接收端应拒绝
  scope: "content_publications",
  complete: true,
  mode: "full_snapshot",
  snapshot_id: "sha256指纹",
  generated_at: "ISO时间",
  units: { views: "万", promo_views: "万", price: "元", promo_cost: "元", fans: "人", completion: "%", interaction: "%", search_rate: "%" },
  counts: { contents: 0, publications: 0, pending_contents: 0, company_posts: 0, company_accounts: 0 },
  data: {
    contents: [],         // 达人合作内容，嵌套每个平台的发布明细
    pending_contents: [],// 界面上的待填写排期占位，不能当作已发布
    company_posts: [],   // 公司账号发布，独立业务
    company_accounts: [] // 预设公司账号
  }
}
```

- 每个顶层业务记录都有 `id`、`source_key`、`record_version`。
- 所有ID规范为字符串；不要转成数字、昵称、链接或“平台+昵称”作为主键。
- `source_key`带类型前缀，ID部分经过URL编码。接收端可直接用 `(source, source_key)` 唯一约束。
- 发布明细子表使用 `(source, content_id, publication_id)` 唯一约束，不能仅以平台去重。
- `record_version`包含这条记录的所有导出值。排期改价/改BD等即使没有更新内容的 `updated_at`，也会改变指纹。不能只按 `updated_at` 判断是否更新。
- 日期 `YYYY-MM-DD` 是业务日，不要按UTC转成上一天；时间戳保持源值，空时间为 `null`。
- `counts`是接口集合长度，包含尚未填全的内容/发布明细，**不能直接等同于品宣ROI的已发布数量**。做统计应按发布日期、数据类型等另定一致口径。

## 5. 达人合作内容 `data.contents[]`

| 字段 | 含义 |
|---|---|
| `id / source_key / record_version` | 源内容ID / `content:<编码ID>` / 记录指纹 |
| `origin` | `schedule`关联排期；`manual`手动添加 |
| `auto_created` | 是否由旧版排期自动补建；不代表已经有真实发布链接 |
| `schedule_id` | 关联排期ID；没有则null |
| `schedule_missing` | 有关联ID但找不到排期时为true，应保留并提示来源关联缺失 |
| `kol_id` | 达人库ID，未关联则null |
| `talent` | 达人昵称；关联排期时使用排期中的值 |
| `category_direction` | 达人类型，当前使用的类型维度；不使用已弃用层级tier |
| `work_type` | 作品类型 |
| `price` | 合作费，元；每条内容仅一份，不要按发布平台重复累加 |
| `fans` | 填写的粉丝数，单位人 |
| `bd_id / bd_name / bd_color` | 商务负责人，含品宣主管；仅身份展示字段 |
| `schedule_date / schedule_status / schedule_deleted_at` | 排期日期、状态、排期删除时间；排期已删不自动等于内容已删 |
| `payment_status / payment_status_label` | 与内容发布列表一致的付款标签：`none`无需付款、`unpaid`未付款、`applied`已申请、`partial`部分付款、`paid`已付款 |
| `main_publication_id / main_platform` | 第一条发布明细对应的ID/平台；无明细时null/空串 |
| `publications` | 下节所述平台发布明细数组，保留源顺序，第一项为主平台 |
| `created_at / updated_at` | 内容记录的源创建/更新时间，不能代替记录指纹 |

付款标签只反映列表现有口径，已归档结算显示已付款；它不是财务流水接口。不会附带银行账户、发票、人员密码等其它模块资料。

### 发布明细 `publications[]`

| 字段 | 含义 / 单位 |
|---|---|
| `id / is_main` | 明细ID / 是否第一条主平台明细 |
| `platform / date / link` | 平台、发布日期、链接 |
| `views` | 播放量/阅读，**万**；0.05表示500，12.5表示125000 |
| `likes / collects / comments / shares` | 点赞、收藏、评论、分享数量 |
| `completion / interaction / search_rate` | 完播率、互动率、看后搜率，百分数值；12.5表示12.5%，不是0.125 |
| `nat_exposure / comp_exposure / search_views` | 自然曝光、组件曝光、看后搜量；保持源填写值，不随views自动乘10000 |
| `attr_direct / attr_indirect / attr_search / attr_audience` | 直接归因、简介归因、看后搜归因、人群获取；保持源填写值 |
| `attr_store` | 店铺表现文字 |
| `cpa3` | CPA3源填写值，原编辑器未统一标注单位，不自行换算 |
| `promo_views` | 投流播放量，万 |
| `promo_cost` | 投流费，元；按实际明细累加一次 |
| `snapshot_day` | 数据采集时点：空串、d0、d3、d7或d30 |
| `snapshot_at / day7_recorded_at` | 采集时间、兼容旧版第7天记录时间，未填为null |
| `daily_stats` | 已存的逐日快照数组：`date / likes / comments / fetched_at`；空数组表示没有，不会触发平台抓取 |
| `mat_downloaded / mat_uploaded / mat_note` | 素材下载状态、上传状态、备注 |
| `legacy.nat_reads` | 历史自然阅读原值；已从当前界面移除，仅存档 |

数值未填写是 `null`，明确填零是 `0`，必须区分。接口不从抖音等平台重新抓取，也不生成未填写的指标。不输出界面筛选条件或个人自定义列偏好；隐藏列的业务数据照常输出。

## 6. 待填写占位 `data.pending_contents[]`

这是“有排期，但没有内容记录”的占位，包含历史、当前和未来未删除排期；和当前内容发布页面一致，按是否已有内容关联判断。

字段：`id`为排期ID，`source_key`为 `schedule:<编码ID>`；`status="pending_content"`；另有 `schedule_id / kol_id / talent / category_direction / work_type / price / bd_id / bd_name / bd_color / schedule_date / schedule_status / schedule_deleted_at / payment_status / payment_status_label / platforms / created_at / updated_at / record_version`。

- `platforms`是计划发布平台，不能当作已经发布。
- 占位补填后，`schedule:…`会消失，出现 `content:…`；通过 `schedule_id`可以关联前后过程。
- 导入后单独标记待填写，不累计到已发布数；不要又把占位金额重复记入发布合作费。

## 7. 公司账号

### `data.company_posts[]`

| 字段 | 含义 |
|---|---|
| `id / source_key / record_version` | 公司发布ID / `company_post:<编码ID>` / 指纹 |
| `accounts` | 所选账号名称数组，可能多个；已包含平台后缀，按原值展示 |
| `date / title / link / hot / note` | 发布日期、标题说明、发布链接、是否爆款、备注 |
| `created_at / updated_at` | 源时间 |
| `legacy.platform / views / likes / collects / comments` | 历史版本遗留字段原值；现界面已不填写，不能当作当前完整指标。legacy内views的旧录入单位未统一确认，禁止直接和达人views相加 |

公司发布一条记录选三个账号仍是一条公司发布记录；如运营系统需要按账号展示，可建关联表，不要生成三份独立可编辑的源发布记录。

### `data.company_accounts[]`

包含 `id / source_key / name / record_version`，`source_key`为 `company_account:<编码ID>`。账号预设被移除时，历史发布中的名称仍保留，不能连带删除历史发布。

## 8. 导入和删除规则（实现时必须遵守）

执行下面步骤前先获取单任务锁，并一直持有到事务和ETag保存完成；第3条是锁的具体要求。

1. **先取完整响应**：检查HTTP状态、JSON Content-Type、版本1.0、source=pinxuan、environment=production、scope、complete=true、mode=full_snapshot。
2. **校验集合**：四个data数组必须都存在；记录/子记录ID必须存在且唯一；实际长度与counts完全一致（publications是所有contents的明细数量之和）。字段类型错误或不完整响应终止整轮同步。未知版本也不更新旧数据。
3. **取得单任务锁**：多进程部署必须用数据库/Redis锁；整个“请求→导入→保存ETag”只能有一个任务运行，立即同步也用同一锁。
4. **事务更新**：按 `(source, source_key)` upsert；已有记录更新来源字段；已标记移除而重新出现的记录恢复为有效。不同record_version才需要写入。运营系统自己维护的字段独立保留。
5. **更新子表**：当前内容的publications以本轮完整数组为准，按 `(source, content_id, publication_id)` upsert，旧子项缺失则标记移除。不要用平台/昵称/链接猜重复。
6. **处理源端删除**：仅对 `pinxuan + content_publications` 导入范围内、已成功导入过而本轮缺失的记录标记 `source_deleted=true`。保留历史供追溯，不物理删除整张表，也不清理运营系统原有记录或其它来源。
7. **异常减少先保留**：若已有数据而返回全空，或待移除数量超过约定阈值（建议超过上次总量20%，且至少5条），暂停应用整轮快照、保留上次ETag并提醒管理员核对。确认后才能应用该快照，防止误操作/源数据恢复造成大批误清理。
8. **提交成功才记游标**：ETag、snapshot_id、最近成功时间、计数和导入变更量与数据同事务提交，或在数据提交成功后可靠写入。失败回滚，不推进ETag。丢失游标可重新全量upsert，不能产生重复。
9. **失败保持上次值**：401、503、网络错误、HTML、JSON解析失败、字段校验失败都不执行删除；304没有正文，也不能当作空数组。
10. **只读来源字段**：运营系统展示最后成功同步时间；不反向修改品宣。建议每5分钟同步，失败退避重试，避免无限快速重试。

硬删除没有历史删除事件可补发，完整快照的“本轮缺失”是首版删除依据。不要自行改成 `updated_at > 上次时间`，否则会漏掉删除、排期带动的改价和商务信息变化。

## 9. 服务端读取示例（Node.js 18+）

下面只负责取数和顶层检查；数据库事务、嵌套字段验证、单任务锁、删除保护和调度仍由运营系统实现。

```js
async function fetchPinxuanSnapshot(lastCommittedEtag) {
  const url = process.env.PINXUAN_CONTENT_API_URL;
  const token = process.env.PINXUAN_CONTENT_SYNC_TOKEN;
  if (!url || !token) throw new Error('品宣同步配置缺失');
  if (url !== 'https://pinxuan.shiganneibu.com/api/integrations/v1/content-publications') {
    throw new Error('品宣接口地址不匹配');
  }
  const headers = { Authorization: `Bearer ${token}`, Accept: 'application/json' };
  if (lastCommittedEtag) headers['If-None-Match'] = lastCommittedEtag;
  const response = await fetch(url, {
    method: 'GET', headers, cache: 'no-store', redirect: 'error',
    signal: AbortSignal.timeout(30000)
  });
  if (response.status === 304) {
    if (!lastCommittedEtag) throw new Error('首次同步不应返回304');
    return { unchanged: true };
  }
  if (response.status !== 200) throw new Error(`品宣接口失败：HTTP ${response.status}`);
  if (!(response.headers.get('content-type') || '').includes('application/json')) {
    throw new Error('品宣响应不是JSON');
  }
  const snapshot = await response.json();
  if (snapshot.schema_version !== '1.0' || snapshot.source !== 'pinxuan' ||
      snapshot.environment !== 'production' || snapshot.scope !== 'content_publications' ||
      snapshot.mode !== 'full_snapshot' || snapshot.complete !== true) {
    throw new Error('品宣快照范围或版本不匹配');
  }
  for (const key of ['contents', 'pending_contents', 'company_posts', 'company_accounts']) {
    if (!Array.isArray(snapshot.data?.[key]) ||
        snapshot.counts?.[key] !== snapshot.data[key].length) {
      throw new Error(`品宣快照不完整：${key}`);
    }
  }
  const etag = response.headers.get('etag');
  if (!/^[a-f0-9]{64}$/.test(snapshot.snapshot_id || '') ||
      etag !== `W/"${snapshot.snapshot_id}"`) throw new Error('快照标识不匹配');
  // 调用方接着执行第8节要求的嵌套校验、变化数量审核和事务导入。
  // 此时仅返回etag，绝不能在数据库提交前把它存为“已同步”。
  return { unchanged: false, snapshot, etag };
}
```

## 10. 联调交接清单

双方接入时建议核对这些情况（本次本地实现未运行端到端联调）：

- 手动内容与排期关联内容都能带入，昵称、价格、类型、BD正确；旧ID数字/字符串不会重复。
- 一条合作三平台仍只有一份合作费，三个平台的链接与指标都保留。
- `views=0.05`正确显示500或0.05万，`null`不会变成已填写的0。
- 改排期价格/BD后，运营系统能更新，即使content.updated_at没变。
- 公司账号多选、爆款、备注、预设账号和历史遗留数据都保留。
- 内容删除、子发布删除、占位转内容及删除后恢复，导入副本能正确更新。
- 无变更返回304；模拟同步失败后，目标已有记录保持不变。
- 不同来源的运营数据不被清理，运营自己填写的字段不被覆盖。
- 真正建立自动同步前，确认正式密钥已经部署，接收端不连接本地历史副本。

## 11. 品宣端维护说明

- 新模块：`content-publications-api.js`；路由注册在 `server.js`，现有 `/api/data` 和三方合并逻辑保持原样。
- 源数据直接读取当前进程 `DATA_DIR` 下的 `db.json`，不写业务数据库，不执行前端初始化迁移。
- `contents / schedules / company_posts / company_accounts` 必须是数组（可以为空），ID缺失/重复、数值无法解析等会返回503，不能兜底成空快照。
- 字段采用白名单；新加业务字段需要同时更新导出和本文。已弃用但曾保存的字段置于legacy中。
- 部署只更改本应用的环境变量和接口；不需要改运营系统域名、nginx或其它PM2服务。
- 禁用方式：移除 `CONTENT_SYNC_TOKEN` Secret并重新部署；运营系统会同步失败并保留上次结果，不会清空。
